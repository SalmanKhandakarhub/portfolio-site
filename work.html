Multi-Tenant SaaS Platform

The problem. Multiple construction enterprises needed to use the same platform while keeping their data completely isolated from other tenants.

02

Real-time chat across multiple workers

The problem. Messages were arriving only some of the time. The connection manager kept its client list in memory, so delivery only worked when sender and recipient happened to land on the same worker — roughly one time in four.

What I built. Moved every delivery path onto Redis pub/sub channels keyed by tenant and user, so any worker can reach any connected client. Along the way I found the disconnect logging was swallowing its own exceptions and fixed that too.

1-in-4 → 100% delivery Read receipts Reconnect handling
WebSockets · Redis pub/sub
FastAPI · Uvicorn
03

Self-hosted video meetings

The problem. Video calls dropped after a few seconds, and a hosted provider would have added a per-minute bill to every customer conversation.

What I built. A self-hosted Jitsi stack behind a custom domain with SSL, nginx WebSocket proxying, and long-lived connection timeouts. The dropped calls turned out to be a missing UDP rule on the media port — one firewall line, found by reading the media server's own logs rather than guessing.

Zero vendor minutes Custom domain + SSL Stable long calls
Jitsi · Docker Compose
nginx · AWS ALB & ACM

05

Production hardening and secrets

The problem. Database credentials lived in a file on the server, and services didn't come back cleanly after a restart.

What I built. Credentials moved into AWS Secrets Manager and are injected at startup through an IAM role attached to the instance — nothing sensitive on disk. The API, worker, and scheduler now run as grouped systemd services that start, stop, and restart together.

No credentials on disk Least-privilege IAM Restart-safe services
AWS Secrets Manager
IAM · systemd · Poetry
